# Fiberline — Fiber Network Operations App

## Structure

```
fiber-network-app/
  backend/    Express API + PostgreSQL/PostGIS (Steps 1–2)
  frontend/   React + Leaflet map UI (Step 3)
```

## Running it

**1. Database + API**

```
cd backend
cp .env.example .env      # set your Postgres credentials
npm install
npm run migrate
npm run dev                # http://localhost:4000
```

To start over with an empty database: `cd backend && npm run db:reset` (see `backend/README.md` for the lighter `--truncate` option and the manual equivalents).

**2. Frontend**

```
cd frontend
npm install
npm run dev                # http://localhost:5173, proxies /api to :4000
```

## How the map maps to your requirements

| Requirement                            | Where it lives                                                                                                                         |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| #1 Poles + cables on a map             | "Add pole" / "Draw cable" modes — real OSM map, real coordinates                                                                       |
| #2 Enclosures on poles                 | "Add box" mode — click a pole, attach a box                                                                                            |
| #3 Core in/out per box                 | Box documentation panel (right side) — every core landing at a box, plus the splice table showing exactly which core connects to which |
| #4 Full box documentation              | Same panel — `GET /enclosures/:id/documentation`                                                                                       |
| #5 Drop cable customer label           | Drop cables carry a `customer_label`, shown on the cable and in the box doc                                                            |
| #6 Where a fiber goes                  | Cable detail panel → "Trace" on any core, walks the splice chain end-to-end                                                            |
| #7 Bring a connection from another box | "No spare cores here" button in the box panel → BFS to nearest box with capacity + the path                                            |
| #8 Customer location lookup            | "Locate customer" mode — click the map (or type an address) and the app answers **can we serve this, from which box, and what will the drop cost**: `GET /api/serviceability/check`       |

Extras on top of the original list: cables show their name label on the map once zoomed in (≥ zoom 15, all three map providers); boxes show their code the same way at ≥ zoom 17 (and on hover/selection at any zoom, so dense areas stay readable); the new-splice form spotlights a fiber's cable on the map while you hover its entry (custom dropdown, all providers); splices accept a free-text note (shown in the records table, edit form, and wiring view); and the box wiring view is built around explicit numbered splice pairs (S1, S2, …) — each pair's two fiber ports share a color and tag, joined by a wire, with a plain-text splice map below that highlights the same pair on hover.

**Field work — worksheets and QR tags:** select a box and press *Splice worksheet* (or *Work order* in the box documentation header) and the app builds the checklist for that closure **from the box's own documentation** — `GET /api/work-orders/:boxId`, plus `/text` for a phone-friendly plain-text copy. Nothing on the sheet is invented: every line is something the documentation already says. A splice whose recorded loss is over the app's 0.5 dB limit leads the sheet ("Re-splice CBL-F1 #1 ↔ CBL-D2 #1 — recorded loss 0.75 dB is over the 0.5 dB limit — tray 3/A"), then damaged fibres, empty splitter ports (with the sleeves and pigtail a new drop needs), splitters with no input fibre, splices recorded without a reading, and any mid-span through-joint meeting in the box (saying whether the link was recorded or inferred from cable naming). Spare fibres are listed as *information* — the answer to "which core do I use?" — and the four close-out steps (photograph the trays, record every loss, update core statuses, close and sign) are always at the end. Materials are counted across the rules, so two joints mean two sleeves and nobody has to add them up. The sheet prints (`@media print` drops the map and both panels and prints the checklist in ink), ticks off step by step on a phone (kept per work order, so tomorrow's sheet is not yesterday's half-done job), downloads as `.txt`, and renders a "Fibres in this box" table with each core's far end. A rule that cannot read the documentation degrades to one warning line on the sheet instead of failing the request — a worksheet that prints with a gap beats a 500 in the van.

**QR tags — scan a box, get its documentation:** every box and every pole can carry a sticker that opens its documentation directly. `GET /api/qr/box/:id.svg` (also `pole`, `cable`, `customer`, and `enclosure` as an alias for box) returns an SVG QR code whose payload is a deep link into *this* deployment — `<your app>/?box=<uuid>` — and the app reads that on load and opens that box's panel, so scanning a pole never means searching the map. The base URL is chosen in the order `?base=` (the browser passes its own origin, which is the only answer that is always right: dev serves the app on :5173 and the API on :4000) → `APP_BASE_URL` (for scripts that print labels) → the request's own origin. A tag is only issued for something that exists — a sticker that scans to "not found" is worse than no sticker — and `GET /api/qr/:kind/:id/link` says what a tag would carry before you print fifty of them. The panel's *QR tag* button shows the sticker as a printable label sheet (1–24 copies, with the code printed under it) and offers the SVG, a copy of the link, and the link itself. The QR encoder is in this repo (`backend/src/utils/qr.js`, no new runtime dependency): byte mode, versions 1–10, all four error-correction levels, ISO mask selection, and its matrices are pinned against python-qrcode in `backend/tests/qr.test.js` — 204/204 identical across a payload sweep — with the printed tag read back by OpenCV in the real-Postgres check.

More ops details: the draw-cable form defaults to a 1-fiber drop when the destination is a customer box and 12 cores otherwise; spliced cables march their dashes on the Leaflet map (drops march faster); splitters can be cascaded (`input_port` — a splitter fed by a free port of another splitter, migration `20260101000011`, guarded against deleting a parent that still feeds a child); each IN fiber in the wiring view shows what its far end connects to in the upstream box; and splitter names/notes are written in plain language (no UUID fragments).

**Loss budgets (req #6+):** the Trace button on any core now also computes the optical loss budget for that path — `GET /api/fiber-cores/:id/loss-budget`. Fiber loss is `length_m × attenuation_db_per_km` (0.35 dB/km singlemode default, overridable per cable in the cable editor; a mid-span split copies the override to the downstream half), each splice adds its measured OTDR/power-meter reading or a planning default (0.1 dB fusion / 0.3 dB mechanical), and every splitter the path crosses adds its insertion loss (G.671 planning values, or the measured `splitters.loss_db`) — cascade parents included. The total is compared against the OLT budget (GPON Class B+ 28 dB, XGS-PON N1 29 dB, P2P 24 dB — per-project via `project_settings`, migration `20260101000012`, editable from the budget card) and verdicts come back OK / MARGINAL / FAIL with a 3 dB safety margin. The path list shows a running loss total per segment, color-coded teal (measured) vs amber (assumed default) vs red (flagged). Free QC win: any splice whose recorded loss exceeds 0.5 dB is auto-flagged as a bad splice — in the trace budget and in the box documentation panel (`qc_flags.bad_splices`).

**Outage analysis — "simulate box failure":** select a box and hit *Simulate failure*; the app takes that box's splice/splitter state out of service and answers who goes dark. `GET /api/impact/simulate?kind=box&id=<uuid>` is deliberately box-only — cables are spans, not failure targets. The existing light path is followed from the failed box through connected splitter outputs, cascades and downstream splices; the cable that brings light **into** the box stays lit and is never painted red. The cascade stops when the next fibre, splice, or splitter port is not connected.

**What counts as dark:** a fibre is dark when the headend's light reached it before the failure and does not reach it now — light leaves the OLT's root cores and travels splices (either way), splitter ports (input → output only: light never flows backwards through a splitter) and mid-span continuations, and it does not pass through anything that failed. That definition gives the honest answers:

- the span that *feeds* the failed element is **not** dark: it still carries light up to the break, and the box it came from is still lit;
- failing a mid-span joint reddens the joint, the half below it and the drops behind those customers — not the whole route back to the OLT, and not the branches that merely share an upstream box;
- a fibre whose light has a second path (a second run into the same box, a ring) stays lit: losing one path is not an outage while another is up;
- failing the headend's own box is different — that is the light source, so everything goes dark;
- every fibre *joined inside the failed box* is out — the splice, the splitter, the mid-span joint live in that box and die with it — so the cable carrying it is drawn red whatever the core's status column says. A `PATCH /api/fiber-cores/:id` (or an import) can set a joined core back to `available`; the joint in the database is the stronger evidence, and the panel must never report a customer down while the map draws their drop as if nothing happened;
- a span is one physical cable but many fibres, so a cable that lost *some* of them is reported (and drawn) as **partly out** — `cores_dark` / `cores_in_service` / `partially_dark` on each `affected.cables` entry, `affected.partial_cable_count`, a broken red line on the map, and `+N partly out` next to the count in the panel — never as a span that is gone. Both numbers are counted in *light*: a fibre counts only if the database joins it (a splice, a splitter's input, a port's output) or it reaches the root. Spares are not counted — an unused strand cannot go dark — and neither is a status column on a strand nothing joins: a leftover `spliced` row must not turn a span whose every lit fibre is out, the cable hanging off a failed box's splitter port among them, into a "partly out" line the field reads as still lit.

Direction is what makes this work: light flows from the headend root (`headends.root_enclosure_id`). Without one the app says so and walks both ways from the failure point, which may include the feeding span and lit branches — set the root on the OLT box and the red follows the light.

The answer is `{ affected_count, affected{ customers, boxes, cables, cores }, upstream_reroute_candidates, unreached, warnings }` — each affected customer carries the label, the hops below the failure, its serving box and `path_through_failure` (the exact fiber-by-fiber route its light used to take).

**The column is the app's job, not yours.** Starting the API applies the migrations this build has
that the database does not, and if `cables.continues_cable_id` is missing it adds it and links the
halves of every mid-span split it can match — on a database whose ledger already claims those
migrations ran, where `npm run migrate` answers "Already up to date" and changes nothing. It is
reported in the startup output and it never fails the API: a database that is down, or a user without
DDL rights, prints what it could not do and the app carries on inferring links from cable naming. Set
`SCHEMA_BOOTSTRAP=off` to leave the schema entirely to your own process (`npm run migrate`,
`npm run db:schema`, `npm run db:link-splits` all still work exactly as before).

**The mid-span link in the API:** every cable the API returns says what it continues, whether or not the database has the column. `GET /api/cables` (and `GET /api/cables/:id`, and each entry in a failure report's `affected.cables`) carries:

```json
{ "continues_cable_id": "…", "continues_cable_code": "CBL-F1",
  "continues_at_box_id": "…", "continues_at_box_code": "BOX-MID",
  "continuation_inferred": false,
  "continued_by": [ { "id": "…", "code": "CBL-F1-B", "at_box_code": "BOX-MID" } ] }
```

Upstream is one field pair, exactly like the column; downstream is a list, because a span can be split more than once. When the database has no `cables.continues_cable_id`, the same fields come back with `continuation_inferred: true` and the link the app worked out from the naming rule — so a client never has to know which kind of database it is talking to, and the SQL never names a column that is not there. The cable panel shows it as *"Continues CBL-F1 through BOX-MID (inferred from cable naming)"* / *"Split into CBL-F1-B at BOX-MID"*.

**Mid-span closures:** inserting an enclosure into an existing cable cuts that cable in two — the upstream half keeps its cores and now ends at the new box, and a downstream half continues from it. The two halves are one fiber, so the downstream row records `cables.continues_cable_id` (migration `20260101000014`, which also backfills splits that already existed where the pairing is unambiguous). Every joint-walking view follows that link: the failure simulation paints the whole chain below the inserted box — the joint and everything the joint fed, while the half that feeds *it* stays lit — and counts its customers whether the cores were already lit (*the route auto through-splices live cores at insert time*) or merely available when the box went in, the fiber trace shows the step as *through <box> (fusion splice)* and prices it at a fusion splice in the loss budget, and the customer path reads `CBL-F1 #1 → through BOX-MID → CBL-F1-B #1`. A hand-made pair of halves with no link is still reported honestly — the simulation says the cores behind the closure are not reachable from the root and points at `continues_cable_id`. **You do not have to migrate for this to work.** When the column is absent the app applies the same rule at read time — a downstream cable named `<upstream code>-B` starting where the upstream one ends, same type and core count, split points within 25 m — so the failure simulation, the trace and the loss budget walk across an inserted closure either way, and the report says `N mid-span cable links inferred from cable naming` instead of failing. Recorded links always win: once the column exists, a `NULL` means "not a continuation" and is never guessed. **To record the links explicitly: run `npm run migrate`** — migration 14 adds the column, and migration 15 (`20260101000015_repair_cable_continuations.js`) is a repair pass that ensures it regardless of what the ledger claims, for the case where a failed run left the ledger and the database disagreeing (a recorded migration never runs again, so nothing else can recover that). Until you do, nothing breaks and nothing is switched off: the absence is reported as a *notice*, not a warning — the API startup banner prints `· Mid-span cable links: … links are inferred from cable naming … Everything works` (where a real gap prints `!`), the outage report adds `N mid-span cable link(s) inferred from cable naming` alongside its results, and the insert-enclosure route answers `summary.continuation_recorded: false, continuation_inferred: true`. If the API's own read of the column fails — a stale cached schema answer, or a column dropped behind a running process — it re-checks, drops the column from its query and infers the links rather than failing the request. `npm run db:schema` in `backend/` prints which database the API is really talking to, which migrations are applied, whether the columns are there, and how many splits are linked — plus any pair that still looks unlinked, exit 1 when something needs attention (the answer to "but I *did* run migrate"). Migration 14's backfill only links pairs it can be sure of, so for a split it skipped: `npm run db:link-splits` lists them (read-only) and `-- --apply` links them; a downstream cable you renamed can be linked explicitly with `-- --child CBL-F9-B --parent CBL-F9`. The failure simulation names the pair in its own warning when an outage is blocked by an unlinked split.

How a leg is counted as a customer: when its cable carries a `customer_id` or `customer_label`, when the core is `terminated`, when the core is a lit (`spliced`) strand of a `drop` cable — a drop exists to reach exactly one premises, so it counts even if nobody typed a label — or when a lit core lands in a `terminal` customer box. Legs inferred that way are listed as *Unlabelled drop on CBL-…* (with the reason) instead of being dropped from the list, and `affected.unnamed_count` reports how many there are; spare (`available`/`reserved`) strands never count. So a red drop cable always has a customer behind it in the count.

Direction comes from a **headend**: migration `20260101000013` adds a `headends` table (one row per OLT/CO/PoP — `code`, `site_type`, and `root_enclosure_id`, the box the first feeder lands in) plus `/api/headends` CRUD. Every trace is rooted there, so a failure below a splitter never reports the customers on other ports, and a sibling branch spliced off the same feeder core at the same box stays lit. If no headend is configured, the service first infers source boxes from the cable orientation (plant cable leaving, no plant cable arriving; a box with only drops is never guessed to be an OLT). The response labels that `direction_source: "inferred"`, names `inferred_root_boxes`, and the panel says the direction was inferred while still keeping the upstream feeding span out of the red set. Set a headend/OLT root to make the result explicit. If the network shape has no source, a box failure still uses a box-endpoint fallback: connected output fibres are reported and the IN cable is excluded, with `direction_source: "box_endpoints"`. A genuinely directionless lower-level analysis is marked `direction_source: "none"`, warns that it may include the feeding span and branches that still have light, and offers the one-click *Set this box as the network root*. Restoration suggestions reuse the requirement-#7 BFS (`capacityGraph`), started at each box where affected customers would have to be re-spliced, skipping boxes that are dark (you cannot patch light through a dead splice) and preferring the nearest still-lit box with spare cores; when no cable path exists the suggestion says so and names the nearest lit box plus the distance a new span would cover.
**What a box can actually take:** the box panel now answers the question the field asks at the open closure — *how many ports are left here, and which ones?* Each splitter is listed with its ratio (`1:8`), a capacity line (`1:8 splitter · 4 of 8 free (5, 6, 7, 8)`), the insertion loss the optical budget will charge for it (`10.9 dB measured` when a technician recorded one, `10.5 dB planned` from the G.671 table for the ratio when not), and a port table that names what is on every port: the **customer label from the drop cable** (`CUST-10209` — the thing printed on the tag), `→ Splitter 1:4` for a port feeding a cascaded child, `damaged — not usable` for a broken port, or `free`. The counts are the API's, not the panel's: one function (`summarizePorts`) defines a free port for the whole app, so the panel badge, the splice dropdown and (below) the capacity checks can never disagree — and a damaged port is never offered as capacity, which is how somebody ends up on a pole with a drop cable and nowhere to land it. Splitters can now be documented up to 1:32.

**Serviceability check — "can we serve this address?":** the sales/CSR question, answered in one call. `GET /api/serviceability/check?address=House 12-B, Street 4` (or `?lat=&lng=` — the map click in *Locate customer* mode), with `/check/text` for a printable/phone copy and `/check/sheet` for a printable **install work order** for the box it picked. The reply is built in the order the work happens, because that is the order the question is asked:

- **which box** — every box within the search radius with its free splitter ports and spare fibres, *nearest* and *serving* reported separately. The interesting case is the one that made this worth building: the nearest box is full, so the answer says "NAP-12 is closer (18 m) but it has no free port and no spare fibre" and builds from NAP-14 (78 m) instead. Every box is an alternative you can click through to on the map;
- **what the connection needs** — a free splitter port (assign it), a splitter that is not installed yet, or capacity work at a box that has room (which names the box to bring capacity from, via the existing `find-source` walk). A full box is still *serviceable* — with work, priced as such, and flagged as needing a survey rather than being quietly quoted;
- **the run** — the street route from OSRM when it answers, otherwise the straight line × 1.25, and the answer says which one it used, on the verdict itself (`drop.source`) and in the confidence (`high` needs a measured route);
- **the price** — cable (measured length + slack), one crew for the drop, one fusion splice, a splitter if one is needed, and per-metre extension if the property is beyond drop range. Given as a **band** (`band.low/typical/high`, ±15% on the length only), *not* a single number, with every line itemised and the rates printed on the answer — a CSR can show the customer where PKR 7,710 comes from. Rates are project settings (`/api/settings`, migration `20260101000016`), so a manager sets the cable price once and every quote follows; the defaults are planning values (PKR 45/m cable, 2,500 a drop, 350 a splice) and the originals are always visible;
- **the answers that are not "yes"** — beyond `max_drop_m` (default 150 m) it is a build (`build_required`, priced as an indicative extension and flagged for survey), beyond `max_extension_m` (500 m) it is a refusal with the distance to the nearest box in it, and "no box found" is reserved for a network with nothing on the map — if the nearest box is simply outside the search radius, the answer says so instead.

**Addresses without a geocoder:** most serviceability questions are about a street the network is already on, so the lookup is local and instant — an **asset code** ("drop to NAP-14 please" works: the code is recognised inside a sentence) or a **customer address already in the database**, scored by token overlap with the house number checked as a unit. "House 12-C" is *not* "House 12-B": a disagreeing house number caps the match below the threshold, and anything short of confident comes back as suggestions on the 404 (with the CSR free to click the map instead) rather than a price for the wrong house. Set `GEOCODE_BASE_URL` to a Nominatim-compatible service and free-text addresses resolve too; without one, `lat`/`lng` is always accepted, which is what *Locate customer* mode passes.

**On the map:** in *Locate customer* mode, click the house — the panel shows the verdict, the serving box, the run, the price band, the cost lines, the next steps and the warnings, with buttons to put the serving box on the map, copy the quote (plain text, no markup — pastes into a CRM or WhatsApp), open the printable quote, or open the install sheet for the crew. Registering the customer prefills the address that was actually checked.

## What's still manual / next steps if you want to keep going

- **The network root** — outage analysis prefers one `headend` row per OLT/CO (the box the first feeder lands in) so downstream direction is explicit. If it is missing, the service infers source boxes from cable orientation and tells you that assumption; set the root from the failure panel to remove the caveat. Only a network whose shape has no source remains undirected and may over-report.
- **Pole failures are geometric** — spans through a failed pole are found by proximity to the pole (default 15 m, `?radius_m=` up to 200 m), not by electrical continuity, so a span routed well clear of the pole is not counted.
- **Auth** — no login/roles yet; anyone with API access can write. Needed before this touches production data.
- **Cable geometry is exactly what you draw** — a cable is stored as the straight segment between its two boxes when no duct bends are placed, or as a polyline through every bend you click. It is never silently snapped to roads. Set `STREET_ROUTING=on` in the backend env to opt into street routing (via OSRM) if you want road-following geometry instead.
- **Multi-hop cable segments** — a single physical cable currently connects exactly two enclosures. If a feeder cable physically passes through several poles before terminating, model it as several `cable_segments` chained together (mentioned in the schema notes) rather than one row.
- **Editing/deleting spliced cores safely** — deleting a cable currently cascades and could silently orphan splice records; add a guard before going live.
